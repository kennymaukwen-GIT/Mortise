# ① 輸入

- 流水線位置：檔案 → **①輸入** → ②頁面 → ③辨識 → ④結構 → ⑤設定 → ⑥輸出 → ⑦驗證 → 下載
- 交出的產物：來源文件 SourceDoc
- 步驟編號：1.1 到 1.12。修正單指名本階段的步驟時用這組編號。
- 文中標「初始值」的數字都是工程判斷，待評測調整。
- 文中標「需查證」的事項，查證紀錄裡沒有，不可當作已知事實。查證紀錄在 research/ 目錄；其中 vlm.md 與 market.md 兩份在撰寫時不存在，本文件沒有引用這兩個主題的任何事實。

## 這個階段在做什麼

收下使用者的檔案，確認它安全、打得開，轉成後面各階段讀得懂的統一形式。
逐頁記下「這一頁是什麼來源」和「檔案自己帶了哪些線索」，連同使用者想要什麼，交出來源文件 SourceDoc。
這個階段不辨識、不理解，也不用大型 AI；全部是確定性的檢查、讀取與規則判斷。

本階段明確不做的事（留給後面的階段）：

| 不做的事 | 誰做 |
|---|---|
| 找頁面四角、攤平、決定用哪個頁框當頁面、產生工作影像、判斷頁面該不該轉 90 度 | ② |
| 讀出文字與圖形的內容、三種假原生的細判、決定某頁走檔案讀取還是影像辨識 | ③ |
| 判斷來源軟體 | ⑤ |

## 收什麼、交什麼

### 收什麼

①沒有上游產物。它的輸入是使用者的檔案、設定檔、修正單。

| 產物 | 欄位 | 說明 |
|---|---|---|
| 使用者檔案 | 原始位元組 | 一個工作收「1 個 PDF」或「1 到多張影像」，兩者不混收（初始規則）。 |
| 上傳請求 | 檔名、宣稱的檔案類型、上傳途徑、帳號與方案 | 檔名與宣稱類型只當線索，不當依據。上傳途徑分三種：網頁上傳、網頁相機拍攝、API。方案決定限額。 |
| 使用者意圖表單 | 輸出格式、Word 模式、用途模式、已知尺寸、語言、書寫方向、頁面範圍、來源軟體提示、影像類型提示、權利聲明、訓練同意 | 細節見 1.11。 |
| 設定檔 | 限額、門檻、樣式比對表、各步驟版本 | 見各步驟的參數表。 |
| 修正單 Correction | 目標階段與步驟、目標編號、欄位、新值或指示、來源、第幾輪 | 見下方「需要修正單配合的兩件事」。 |

需要修正單配合的兩件事（共同約定裡沒寫，本階段需要）：

1. 修正單的「目標元素編號」在①要能填**檔案編號或頁面編號**。①還沒有元素，只有檔案與頁面。
2. 密碼不寫進修正單。修正單只記「已提供」，密碼本身走一次性的密鑰通道，用完即丟。

### 交什麼：來源文件 SourceDoc

三個通用約定：

- **幾何單位。**①用檔案的原生單位：PDF 用 pt（1 pt = 1/72 英吋），影像用像素。「頁寬為 1」的相對座標要等②定出頁面四角才存在。
- **帶信心值的欄位。**照共同約定記四項：值、信心值（0 到 1）、來源類型、寫入者（步驟編號與版本，例如 1.9 的某版）。從檔案直接讀到的記「精確擷取」；規則算出來的記「量測」；使用者給的記「使用者」，信心值 1.0。
- **「精確擷取」只代表讀得對，不代表內容為真。**例如 Producer（PDF 裡記錄「哪個程式寫出這個檔」的欄位）可能被後來經手的工具改寫。

隨 SourceDoc 交出、由它指到的檔案：原始檔、正規化 PDF、正規化影像、預覽圖、深度等輔助影像。

與②的交界約定（需與②的文件核對）：

- 影像頁：②所說的「原圖」就是①的正規化影像。①只套用檔案標記的方向，不縮放、不裁切、不增強。
- PDF 頁：①不產生工作影像。②自己從正規化 PDF 渲染，或直接取出內嵌的掃描影像；①在 `pdf_page.images[]` 提供像素尺寸與有效 dpi 供②決定解析度。
- 用哪個頁框當頁面由②決定。①的覆蓋率統計以 CropBox（閱讀器顯示的範圍）為分母，並記下用了哪個頁框。

## 各步驟細節

### 1.1 接收

**目的。**把檔案安全地收進來。還沒打開檔案之前，就擋掉明顯超限的。

**做法。**

- 三個入口走同一條路：用戶端先拿到一次性的上傳連結，再把檔案直接傳到「隔離儲存區」。隔離儲存區與正式儲存分開，沒有對外讀取權限。應用伺服器不經手檔案位元組。
- 網頁相機拍攝：產品不做手機 App，所以用手機瀏覽器的檔案選擇欄位叫出原生相機，拿到全解析度的照片。拍攝前在畫面上提示：正對、讓文件填滿畫面、避開反光。這條途徑的 `capture_kind` 直接記「相機拍攝」，因為來源已知。各家瀏覽器實際交出什麼格式、是否保留 EXIF（相機寫在影像檔裡的拍攝資訊），需查證。
- API：與網頁相同的兩段式上傳，另收一個「防重送鍵」，同一個鍵重送不會建立第二個工作。
- 上傳時邊收邊算 SHA-256。
- 限額初檢：位元組數與檔案數，不必打開檔案就能查。頁數與像素要到 1.3 才查得到。
- 工作狀態：已接收 → 檢查中 →（等待使用者）→ 完成，或拒絕。「等待使用者」只出現在三種情況：要密碼、要權利聲明、類型拿不準且設定為要問。

支援的格式：

| 格式 | 是否支援 | 理由 |
|---|---|---|
| PDF | 支援 | 主要輸入。原生、掃描、混合都收。 |
| JPEG | 支援 | 手機照片與掃描最常見的格式。 |
| PNG | 支援 | 截圖最常見的格式。 |
| HEIC／HEIF | 目標支援；授權查清前暫緩上線 | iPhone 的預設拍照格式，一定會有人傳。但解碼牽涉 HEVC（HEIC 內部使用的壓縮技術）的專利與解碼函式庫授權，需查證。暫緩期間請使用者改傳 JPEG。 |
| TIFF | 支援，含多頁 | 掃描器常見的輸出。多頁 TIFF 每頁當一頁。少見的壓縮變體不支援，並明確回報原因。 |
| WebP | 支援靜態影像 | 從網頁存下來的圖常是這個格式。動畫只取第一格。 |
| AVIF | 第二批 | 用量仍少。解碼器授權需查證。 |
| GIF、BMP | 第二批，只取第一格 | 用量少。等有需求再開。 |
| JPEG XL、JPEG 2000 單檔 | 不支援 | 幾乎沒有使用者手上會有。 |
| 相機 RAW（DNG 等） | 不支援 | 不是「不可編輯的文件」的常見形式。 |
| SVG、EPS、AI、PSD、INDD | 不支援 | 這些是可編輯的原始檔或向量檔，不是本產品要解的問題。SVG 與 EPS 另有主動內容風險。處理 EPS 常用的 Ghostscript 授權不符底線（見 research/pdf.md）。 |
| Office 檔（PPTX、DOCX、XLSX） | 不支援 | 已經可以編輯。 |
| 壓縮檔（ZIP 等） | 不支援 | 有解壓縮炸彈風險。多個檔案請直接多選上傳。 |
| 網址 | 不支援 | 讓伺服器代抓網址，可能被用來探測內部網路。 |

注意：.ai 檔常內含 PDF 相容的內容，1.2 會把它判成 PDF。這種情況照 1.2 的「副檔名與內容不符」規則提示使用者，不默默接受。

拒絕時回給使用者的原因碼（產品文案由此對應）：格式不支援、檔案過大、頁數超限、像素超限、檔案損壞無法修復、需要密碼、密碼錯誤、受權限保護、偵測到惡意內容、處理逾時。

**輸入與輸出欄位。**輸入：檔案位元組、上傳請求。輸出：`files[].file_id`、`sha256`、`byte_size`、`declared_ext`、`declared_mime`、`upload_channel`、`original_ref`。

**信心值依據。**確定性步驟，不產生帶信心值的欄位。唯一例外是相機途徑的 `capture_kind`，來源類型記「精確擷取」。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 行動網路上傳大檔中斷 | 完整版本做分段續傳。最笨版本請使用者重傳。 |
| 使用者傳了 200 頁的報告只想救其中 3 頁 | 意圖表單提供頁面範圍；超限時回報「可改選頁面範圍」而不是只說失敗。 |
| 通訊軟體轉傳過的照片被壓縮、拍攝資訊被去除 | 無法補救。1.9 的線索表要能在沒有拍攝資訊時運作。各通訊軟體的實際行為需查證。 |
| 用戶端謊報檔案大小 | 以隔離儲存區實際收到的位元組數為準。 |

**設定檔參數。**（皆為初始值，待評測調整；可依方案分級）

| 參數 | 預設值 | 單位 |
|---|---|---|
| `max_pdf_bytes` | 100 | MB |
| `max_image_bytes` | 50 | MB |
| `max_files_per_job` | 50 | 個 |
| `max_pages_per_job` | 200 | 頁 |
| `upload_url_ttl` | 15 | 分鐘 |
| `retention_days` | 30 | 天 |

**可單獨升級的點。**分段續傳；瀏覽器內的即時相機畫面加對位框；新增格式。

### 1.2 檔案類型判定

**目的。**以內容決定格式。副檔名與瀏覽器宣稱的類型都可以造假或出錯。

**做法。**

- 讀檔頭的特徵碼（每種格式開頭固定的幾個位元組）比對允許清單。HEIC 與 AVIF 共用同一種容器，要再讀裡面的品牌欄位才分得出來。
- 不在允許清單就拒絕。
- 同時符合兩種格式特徵的檔案（多格式混體檔，是常見的攻擊手法）一律拒絕。
- 副檔名與內容不符：以內容為準，記 `ext_mismatch`，並提示使用者。
- PDF 的檔頭允許出現在檔案前 1,024 位元組內，因為真實世界有些 PDF 前面夾了雜訊。
- 候選工具：自寫比對表（只有十來種格式，規則少，首選）；或 libmagic（授權需查證）。

**輸入與輸出欄位。**輸入：原始位元組的開頭。輸出：`container_format`、`ext_mismatch`。

**信心值依據。**確定性步驟，不帶信心值。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 檔頭正確但內容被截斷（下載不完整） | 這一步放行，1.5 或 1.6 解析失敗時回報「檔案損壞」。 |
| .ai、.eps 內含 PDF 內容 | 判為 PDF 並提示不符；使用者確認後才繼續。 |
| HEIC 的連拍或影片序列 | 判為不支援的變體，回報原因。 |

**設定檔參數。**

| 參數 | 預設值 | 單位 |
|---|---|---|
| `allowed_formats` | pdf、jpeg、png、tiff、webp（heic 待授權查清後加入） | 清單 |
| `pdf_header_search_bytes` | 1,024 | 位元組 |

**可單獨升級的點。**新增格式只要加一條比對規則與對應的解碼器，不影響其他步驟。

### 1.3 安全檢查與隔離執行

**目的。**保護系統與其他使用者。確認檔案在限額內才往下做。

**做法。**分七件事。

**(a) 隔離執行環境。**從這一步起，凡是會解析檔案內容的步驟（1.3、1.5 到 1.10），都在隔離環境裡執行。條件：沒有網路、唯讀檔案系統、非特權身分、限制可用的系統呼叫、限制記憶體與 CPU 時間、一個工作一個環境、用完即毀、環境內沒有任何憑證。隔離環境吐出來的資料也當作不可信：在環境外驗證結構與大小後才收。理由：PDF 與影像的解碼器是記憶體安全漏洞的常見來源，這是對我們最主要的威脅。PDFium（查證紀錄建議的 PDF 主引擎）本身不是執行緒安全，平行處理本來就要用多行程（見 research/pdf.md），與「一個工作一個行程」的隔離做法一致。候選技術：gVisor、Firecracker、nsjail、bubblewrap，授權與適用性皆需查證。

**(b) 打開後才查得到的限額。**只讀檔頭取得像素尺寸與頁數，先比對上限，再決定要不要完整解碼。

**(c) 解壓縮炸彈與超大影像。**解壓縮炸彈是指檔案很小、解開後卻大到塞爆記憶體的檔案。對策有四層：檔頭宣稱的像素數先過上限；PDF 單一資料流解開後的大小設上限；PDF 物件總數與巢狀深度設上限；最後由隔離環境的記憶體與時間上限兜底，超過就終止並回報「處理逾時」或「檔案過大」。超過工作像素上限但未超過硬上限的影像，縮小到工作上限以內，並把倍率記進 `normalization_log`。

**(d) 惡意檔案掃描。**用掃毒引擎掃原始檔。要誠實看待它的定位：對我們的主要防線是隔離環境；掃毒是第二道，也是企業客戶做資安審查時會問的項目。候選引擎 ClamAV 的授權需查證；若屬 GPL，按授權底線不能用，見「待你決定的問題」。另一個結構性的保護：輸出檔是由成品文件重新產生的，原始檔的位元組不會流進輸出檔；影像一律解碼後重新編碼。

**(e) 加密的 PDF。**

| 情況 | 處理 |
|---|---|
| 要密碼才能開啟 | 工作進入「等待使用者」。使用者輸入密碼後，在隔離環境內解密。密碼只在記憶體裡用一次，不寫進 SourceDoc、修正單、紀錄檔。錯誤次數達上限就結束工作。 |
| 不用密碼就能開，但帶有「限制修改」或「限制複製」的權限旗標 | 預設：工作進入「等待使用者」。除了每次上傳都要勾的一般權利聲明，使用者要再針對這份檔案確認一次（「作者對此檔設了限制，我確認有權編輯」），才處理並留下紀錄。這是政策決定，見「待你決定的問題」。 |
| 以憑證加密 | 不支援，回報原因。 |

解密工具：pikepdf（底層是 qpdf），授權可用（見 research/pdf.md）。qpdf 對「只有權限限制、沒有開啟密碼」的檔案實際怎麼處理，需查證。

**(f) 主動內容。**記錄 PDF 裡有沒有 JavaScript、內嵌檔案、啟動外部程式的動作、XFA 表單（一種動態表單）。我們從不執行它們。1.5 產生正規化副本時把它們移除。含 XFA 動態表單的檔案，一般引擎畫不出填寫內容，記警告。PDFium 對 XFA 的支援情況需查證。

**(g) 數位簽章。**只記錄「有簽章」。提示使用者：轉出的檔案不是原本簽過的那一份。這是 R8（偽造風險）的第一個掛點。

**輸入與輸出欄位。**輸入：原始檔、`container_format`、方案限額、密碼（若有）、受限制文件的權利確認（若有）。輸出：`files[].security` 全部欄位；通過或拒絕的原因碼。

**信心值依據。**限額與加密判斷是確定性的。掃毒結果照引擎回報記錄，另記引擎與病毒碼版本。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 解碼器當掉或卡死 | 隔離環境終止該行程，工作標為失敗並留下可重現的檔案雜湊，供工程師事後分析。不自動重試超過 1 次。 |
| 掃毒誤判正常檔案 | 回報「偵測到惡意內容」並提供申訴管道；不提供「仍要處理」的按鈕。 |
| 使用者忘記密碼 | 無法處理。明確告知原因，不暗示我們能破解。 |
| 檔頭宣稱的尺寸與實際不符 | 解碼時再驗一次；不符就當作損壞檔。 |

**設定檔參數。**（皆為初始值，待評測調整）

| 參數 | 預設值 | 單位 |
|---|---|---|
| `image_pixels_working_max`（超過就縮小並記錄） | 64 | 百萬像素 |
| `image_pixels_hard_max`（超過就拒絕） | 250 | 百萬像素 |
| `image_side_min`（短邊低於此值就拒絕） | 200 | 像素 |
| `pdf_page_side_max` | 14,400 | pt |
| `pdf_stream_inflated_max`（單一資料流解開後） | 512 | MB |
| `pdf_object_count_max` | 2,000,000 | 個 |
| `pdf_nesting_depth_max` | 32 | 層 |
| `sandbox_memory_max` | 4 | GB |
| `sandbox_cpu_seconds_per_file` | 120 | 秒 |
| `sandbox_cpu_seconds_per_page` | 10 | 秒 |
| `sandbox_wall_seconds` | 300 | 秒 |
| `password_attempts_max` | 5 | 次 |

**可單獨升級的點。**隔離技術可換（行程層級換成微型虛擬機）；掃毒引擎可換或加第二顆；限額可依方案分級。桌面版沒有伺服器的隔離環境，要改用作業系統提供的隔離機制，屆時另行設計。

### 1.4 內容雜湊與重複偵測

**目的。**同一份檔案不要算兩次。同一個工作裡的重複檔案要提醒使用者。

**做法。**

- 檔案雜湊在 1.1 已經算好。本步驟用它做三件事。
- **同一工作內的重複。**兩個檔案雜湊相同：預設只留一份，並在畫面上提示。
- **快取查詢。**①的快取鍵 = 檔案雜湊 + ①的版本 + ①相關設定的雜湊 + 送給①的修正單的雜湊。使用者意圖不放進這個鍵。命中就直接取回上次的解析結果，跳過 1.5 到 1.10。
- **快取範圍。**預設只在同一位使用者之內。跨使用者共用快取會洩漏「別人也傳過這份檔案」，與隱私承諾衝突（R7）。快取條目隨檔案的保留期限一起刪除。
- **給下游的快取設計。**每一頁的條目有自己的 `page_digest`，意圖的每個欄位有自己的雜湊。下游各階段的快取鍵只放它實際讀的欄位。效果：使用者事後加一種輸出格式時，流水線照規則從①重跑到底，但②③④讀的欄位沒變，全部命中快取，實際只重做⑤之後的部分。

**輸入與輸出欄位。**輸入：`sha256`、設定檔、修正單。輸出：`cache.cache_key`、`cache.hit`、重複檔案的警告。

**信心值依據。**確定性步驟，不帶信心值。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 同一張照片被重新存檔或去掉拍攝資訊，位元組不同 | 位元組雜湊抓不到。完整版本另算「解碼後像素的雜湊」。 |
| 同一頁被拍了兩次，內容相近但不相同 | 完整版本用感知雜湊（內容相近的影像會得到相近的指紋）找出來，問使用者留哪一張。 |
| 掃毒病毒碼更新後，舊快取的「乾淨」結論過期 | 快取條目記錄當時的病毒碼版本；超過設定天數就重掃。 |
| 版本升級後誤用舊快取 | 版本在快取鍵裡，升級後自然不命中。 |

**設定檔參數。**（初始值，待評測調整）

| 參數 | 預設值 | 單位 |
|---|---|---|
| `cache_scope` | 同一使用者 | 選項 |
| `duplicate_in_job_policy` | 留一份並提示 | 選項 |
| `rescan_after_days` | 7 | 天 |
| `near_duplicate_distance_max`（完整版本） | 待評測 | 感知雜湊的位元差 |

**可單獨升級的點。**像素雜湊；感知雜湊；頁面層級的內容雜湊（同一頁出現在不同檔案時也能命中）。

### 1.5 PDF 修復與正規化

**目的。**把各種狀況的 PDF 變成一份打得開、不加密、沒有主動內容的副本。後面所有階段都只讀這份副本。

**做法。**

- 工具：pikepdf（查證時的版本是 10.18.2，MPL-2.0）與它底層的 qpdf（Apache-2.0）。兩者可商用、可隨桌面版散布；pikepdf 能修復壞檔、解密、讀寫任何字典（見 research/pdf.md）。MPL-2.0 只要求公開「對 pikepdf 自己的原始檔所做的修改」；不改它就沒有公開義務。查證紀錄建議請法務確認一次。
- 流程：
  1. 用 pikepdf 開啟。索引表壞掉時 qpdf 會嘗試重建，並回報警告。警告全部記進 `repair`。
  2. 有密碼就在這裡解密。
  3. 移除主動內容（JavaScript、啟動動作、內嵌檔案）。不動頁面的內容資料流。
  4. 寫出正規化副本：合併增量更新（PDF 允許把修改附加在檔尾，舊版本內容仍留在檔案裡）、取消網路最佳化排列。
  5. 用 PDFium 再開一次正規化副本，核對兩個解析器讀到的頁數是否一致。不一致代表檔案有問題或有惡意，預設拒絕。
- 原始檔永遠保留、永遠不改。正規化副本是衍生檔，記錄產生它的工具版本。
- 不可使用的工具：PyMuPDF、MuPDF、Ghostscript（AGPL）、Poppler 及包裝它的 pdf2image（GPL）（見 research/pdf.md）。網路上常見的「修 PDF」做法多半靠 Ghostscript，不能照抄。

**輸入與輸出欄位。**輸入：原始 PDF、密碼（若有）。輸出：`normalized_ref`、`normalization_log`、`repair.was_repaired`、`repair.warnings[]`、`repair.page_count_agreement`、`pdf_meta.has_incremental_updates`、`pdf_meta.linearized`。

**信心值依據。**不帶信心值。修復警告的數量與種類原樣記錄；有修復的檔案，在還原度報告的檔案層註記「此檔曾修復，內容可能不完整」（由⑦讀 `repair` 決定怎麼呈現）。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 檔案被截斷，只救回前幾頁 | 比對目錄宣稱的頁數與實際救回的頁數；不符就警告「只救回 N 頁」，讓使用者決定要不要繼續。 |
| pikepdf 打不開 | 退而直接用 PDFium 開原始檔；仍失敗就拒絕，原因碼「檔案損壞無法修復」。PDFium 自己的修復能力需查證。 |
| 修復時默默丟掉物件 | 無法完全避免。靠頁數核對與修復警告提示；⑦的 7A 比對會在版面上看出缺漏。 |
| 重寫後物件編號改變 | 所有索引都指向正規化副本，下游只讀正規化副本，編號一致。 |
| 同一檔案兩次正規化的位元組不同 | 正規化結果存進快取，只產生一次。qpdf 的確定性輸出選項需查證。 |
| PDF 作品集（一個 PDF 包多個檔案） | 不支援，回報原因。 |

**設定檔參數。**

| 參數 | 預設值 | 單位 |
|---|---|---|
| `page_count_mismatch_policy` | 拒絕 | 選項 |
| `strip_active_content` | 開 | 開關 |
| `partial_recovery_policy` | 警告並等使用者確認 | 選項 |

**可單獨升級的點。**加第二個修復引擎做後備；修復警告分級（哪些可忽略、哪些要提醒使用者）要靠真實壞檔累積。

### 1.6 影像解碼與正規化

**目的。**不管進來的是什麼影像格式，後面拿到的都是同一種：方向正確、色彩空間統一、位元深度統一。對後面有用的資訊一項都不丟。

**做法。**

**內部統一格式。**sRGB 色彩空間、每通道 8 位元、無失真壓縮；有透明通道就多存一個通道。選 sRGB 的理由：Office 檔案的顏色就是 sRGB，全線用同一個色彩空間，③量到的顏色才能直接比較。絕不把影像重存成有失真的格式。最笨版本用 PNG 當容器；完整版本可換成編碼更快的無失真容器，待評測。

**逐項處理。**

| 項目 | 處理 | 記錄 |
|---|---|---|
| 方向 | 照檔案的方向標記把像素轉正，然後清掉標記。 | 標記原值與實際套用的轉換。深度等輔助影像要套用同一個轉換。 |
| 色彩描述檔（ICC，記錄「這些數值代表什麼顏色」的資料） | 有內嵌描述檔：照它轉成 sRGB。沒有：RGB 影像假設為 sRGB；CMYK 影像假設為設定檔指定的預設描述檔。 | 來源是「內嵌」還是「假設」。假設的情況，③量到的顏色信心值應該調低。 |
| 廣色域（例如手機的 Display P3） | 轉成 sRGB，超出範圍的顏色會被壓回邊界。 | 被壓回的像素比例。 |
| 位元深度 | 16 位元降為 8 位元；1 位元（傳真式的黑白掃描）展開為 8 位元。 | 原始位元深度。 |
| HDR（高動態範圍） | 只取標準動態範圍的基礎影像，忽略增益圖。 | 有無增益圖。各解碼器的支援情況需查證。 |
| 透明通道 | 保留。另外算出不透明內容的外框。 | `has_alpha`、`alpha_bbox`。實際案例：macOS 的視窗截圖四周是透明的陰影，②可以用這個外框裁掉。 |
| 多影格 | 多頁 TIFF：每頁一頁，略過縮圖用的子影像。動畫 WebP、GIF：只取第一格。 | 影格數。 |
| 像素超過工作上限 | 等比縮小到上限以內。 | 縮小倍率。 |

**保留的中繼資料與用途。**

| 保留什麼 | 給誰用、為什麼 |
|---|---|
| 焦距、等效 35 mm 焦距、數位變焦倍率 | ②。有焦距時，可以從透視變形的四邊形估出比較可靠的長寬比（方法由②決定）。 |
| 深度影像 | ②。R4 說單張照片的絕對尺度不可觀測；深度資料是少數可能的例外。①只原樣取出，不解讀。深度是不是以公尺為單位、哪些手機與拍攝模式會存、解碼器取不取得出來，都需查證。 |
| 拍攝裝置廠牌與機型 | 1.9 的類型線索；②的鏡頭變形先驗。 |
| 解析度標記（dpi） | ②。掃描器寫的 dpi 可以換算實際尺寸；截圖寫的 72、96、144 dpi 只是作業系統的預設值，不代表實際尺寸。①附一個可信度提示，由②決定採不採用。 |
| 寫檔軟體字串、是否經裁切或編輯 | 1.9 的線索；②。影像被裁切過，焦距就不能照原樣使用。 |
| JPEG 品質估計、色度抽樣 | ③。壓縮很重的影像，辨識的信心值應該調低。 |

**刻意丟掉的中繼資料。**GPS 位置、裝置序號、內嵌縮圖、廠商私有區塊。理由是資料最小化：後面用不到，留著只增加隱私風險。

**候選工具與授權。**

| 工具 | 用途 | 授權 |
|---|---|---|
| Pillow | 解碼、方向、基本色彩轉換 | MIT-CMU（見 research/formats.md，由套件登錄資料直讀）。它內建的像素上限保護機制細節需查證。 |
| OpenCV（`opencv-python-headless`） | 解碼、像素統計 | Apache-2.0；伺服器用 headless 套件避開 Qt 的 LGPLv3；所有預編譯套件都內附 FFmpeg（LGPLv2.1），桌面版要另外處理（見 research/image.md）。它讀檔時怎麼處理方向標記與色彩描述檔，需查證。 |

| 解碼器對損壞影像只解出上半張 | 檢查解碼是否回報截斷；截斷就警告使用者，不默默接受半張圖。 |

### 1.7 中繼資料擷取

**目的。**把檔案自己帶的線索原樣讀出來，供後面各階段當證據。①只讀不判斷。

**做法。**

PDF 用兩個工具合起來讀，理由是沒有任何一個授權可用的函式庫能單獨涵蓋（見 research/pdf.md）：

| 資料 | 用什麼讀 | 給誰用 |
|---|---|---|
| Info 字典八個欄位（含 Creator、Producer） | PDFium 的 `FPDF_GetMetaText`，或 pikepdf | ⑤判斷來源軟體（R3）；1.10 的輔助線索 |
| XMP | pikepdf | 同上。Info 與 XMP 互相矛盾時兩份都原樣保留 |
| 五種頁框、旋轉 | PDFium 或 pikepdf | ②決定頁面範圍與尺寸 |
| 使用者單位倍率（`/UserUnit`） | pikepdf 直接讀頁面字典 | ②換算超大頁面的實際尺寸 |
| 圖層清單與預設開關 | pikepdf 讀 `/OCProperties`。PDFium 的公開介面沒有列舉圖層的函式 | ③決定哪些物件算「畫面上有的」 |
| 內嵌字型清單 | pikepdf 讀字型字典 | ③⑤的字型證據；1.10 |
| 是否為 Tagged PDF、文件語言、閱讀方向 | pikepdf 讀文件目錄 | ④的閱讀順序與角色證據（R5）；③的語言選擇 |
| 印刷輸出條件 | pikepdf | ③⑤處理 CMYK 顏色 |
| 註解、表單欄位 | PDFium 或 pikepdf | ②③決定是否畫進工作影像、是否當元素 |

內嵌字型清單的欄位：`font_key`（檔內物件參照）、`base_name`（去掉子集前綴後的名稱）、`subset`（是否為子集）、`type`（Type1、TrueType、Type0 及其子類、Type3）、`embedded`（字型程式是否內嵌）、`has_tounicode`（是否有 ToUnicode，即「字形代碼對應到哪個文字」的對照表）、`encoding`、`writing_mode`（橫排或直排）、`cid_ordering`（中日韓字集的標示，例如代表繁體中文的 Adobe-CNS1）、`descriptor`（字型字典裡的旗標、斜角、字重、上伸下伸等數字）、`pages_used`。

字型的處理界線照查證紀錄的建議（見 research/fonts.md 第 4.5 節）：

- 只讀字型名稱與字型字典裡的數字。這些不涉及複製字型程式，風險最低。
- 不把內嵌字型取出來存檔，不累積成字型庫，不放進輸出檔。
- 讀內嵌字型的嵌入許可旗標（`fsType`）當輔助資訊，列為完整版本，而且只在記憶體裡讀、不落地。做之前請法務確認。

與 R2 的關係：這裡記的是「檔案宣稱的字型名稱」。它是⑤推論字型的證據，不是結論。名稱可能帶子集前綴，也可能是製作軟體自己取的代號。

影像的中繼資料已在 1.6 列出。本步驟對影像另做一件事：PDF 頁面裡整頁大小的內嵌 JPEG，直接讀它原始位元組裡的 EXIF（PDFium 可取得影像的原始位元組，見 research/pdf.md）。若有相機資訊，代表這頁「掃描」其實是手機拍的，記進 `pdf_page.images[].exif_camera_present`，供 1.9 判斷取得方式。

**輸入與輸出欄位。**輸入：正規化 PDF 或原始影像。輸出：`files[].pdf_meta` 全部欄位、`pages[].pdf_page.boxes`、`rotate`、`user_unit`、`annotations`、`fonts_used[]`、`layers_used[]`。

**信心值依據。**全部是「精確擷取」，信心值 1.0，代表讀得對。內容是否為真由使用它的階段判斷。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| Producer 空白、被後製工具改寫、或被人為竄改 | ①原樣記錄。⑤必須把它當成證據之一，不能當成唯一依據。使用者在意圖表單填的來源軟體提示優先。 |
| 中文標題解碼成亂碼 | 保留原始位元組的十六進位表示，不丟資料。 |
| 字型名稱是無意義的代號 | 原樣記錄。⑤靠量測與影像特徵推論。 |
| 頁框從上層頁面樹繼承 | 函式庫會處理；測試集要有這種檔案。 |
| 個人資料（作者姓名） | 保留在 SourceDoc，隨檔案 30 天刪除。不寫進紀錄檔，不用於統計。 |

**設定檔參數。**

| 參數 | 預設值 | 單位 |
|---|---|---|
| `keep_pdf_personal_fields` | Title、Author、Subject、Keywords | 清單 |
| `read_fsType`（完整版本） | 關 | 開關 |
| `metadata_string_max` | 4,096 | 位元組／欄位 |

**可單獨升級的點。**製作軟體字串的比對表（哪些字串代表掃描軟體、哪些代表文字辨識軟體）要用真實檔案慢慢累積；目前沒有現成資料，需查證。

### 1.8 拆頁與頁面統計

**目的。**建立頁面清單。每一頁給一個不會變的編號，並算出後面兩個步驟要用的統計數字。

**做法。**

- **頁面編號。**`page_id` 由「檔案雜湊加檔內頁序」導出。同一個檔案不管重跑幾次，同一頁的編號都一樣，修正單才指得到它。使用者調整頁序只改 `order`，不改 `page_id`。建議③的元素編號把 `page_id` 包在裡面。
- **拆頁方式。**預設是邏輯拆頁：不真的把 PDF 切成一頁一檔，各頁的工作行程各自打開正規化副本、只讀自己那一頁。大檔案若量到讀檔成為瓶頸，再升級成實體拆頁。
- **頁面選取。**照意圖表單的頁面範圍，只為選到的頁建立條目。
- **多張影像。**預設合成一份多頁文件，照上傳順序排頁。
- **PDF 逐頁統計。**用 PDFium 走過頁面物件。PDFium 把頁面物件分成文字、路徑、影像、漸層、Form 五類，並可走進 Form 物件內部（見 research/pdf.md）。Form 物件是一組可重複使用的繪圖內容，裡面還可以再包別的物件。統計項目：

| 統計量 | 定義 | 備註 |
|---|---|---|
| 可見字數 V | 渲染模式不是「不可見」、也沒被後畫的大影像蓋住的字元數 | 渲染模式是 PDF 裡每段文字「怎麼畫」的設定，其中第 3 種是不畫出來。PDFium 會在行尾補上引擎自己產生的換行字元，統計時要排除（見 research/pdf.md 的實測）。 |
| 不可見字數 H | 渲染模式為 3（不可見）的字元數 | 讀取函式見 research/pdf.md。 |
| 被遮住字數 | 繪製順序在某張大影像之前、且外框落在該影像之內的字元數 | PDFium 沒有現成函式，要用物件順序與外框自己算；查證紀錄標為未實測，需查證。 |
| Unicode 對照有誤字數 | PDFium 逐字回報對照有誤的字元數 | 該函式標為實驗性介面（見 research/pdf.md）。 |
| 文字覆蓋率 | 文字外框聯集的面積 ÷ CropBox 面積 | |
| 影像聯集覆蓋率 C | 所有影像外框的聯集面積 ÷ CropBox 面積 | 用粗網格（例如 256 × 256 格）畫外框求聯集，便宜而且夠準。 |
| 最大單張影像覆蓋率 | 最大那張影像的外框面積 ÷ CropBox 面積 | |
| 路徑物件數、路徑線段數 S | 路徑物件與其線段的總數 | 線段數比物件數穩定：有些軟體把整段文字的外框寫成一個物件。 |
| 每張影像的有效 dpi | 像素寬 ÷ 在頁面上的寬度（英吋） | 供②決定工作影像解析度。 |

- **預覽圖。**每頁用 PDFium 渲染一張低解析度預覽，給畫面顯示與選頁用。PDFium 渲染的範圍是 CropBox，且會遵守圖層的預設關閉（見 research/pdf.md 的實測）。
- **線索。**順手統計原生文字的字元分布（中日韓字、假名、韓文、阿拉伯文等各占多少），連同文件語言標記、字型的中日韓字集標示、直排字型標示，記進 `hints`。這讓我們能在第一關就提醒使用者「這份文件有直排文字，目前不支援」，不必等到後面才失敗。

**輸入與輸出欄位。**輸入：正規化 PDF 或正規化影像、頁面範圍。輸出：`pages[].page_id`、`order`、`file_id`、`index_in_file`、`preview_ref`、`page_image_ref`、`pdf_page.stats`、`pdf_page.images[]`、`hints`、`warnings[]`。

**信心值依據。**統計量是量測值，來源類型記「量測」。覆蓋率用外框近似，被裁切路徑遮掉大半的影像會被高估；這個誤差的來源寫進 `evidence`，由 1.9 的門檻留餘裕來吸收。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 掃描頁被存成許多橫條影像，或分成背景層加文字層 | 用聯集覆蓋率而不是單張覆蓋率。 |
| 影像被裁切路徑裁成一小塊，外框卻很大 | 覆蓋率高估。完整版本改用低解析度渲染加物件遮罩來算。 |
| 地圖、工程圖這類有數十萬個路徑的頁面 | 記警告「超複雜向量頁」。①不改判類型；③與⑥決定要不要把它當成影像處理。統計時套用每頁時間上限。 |
| 一頁裡其實排了多個邏輯頁（講義一頁六格、書本跨頁掃描） | ①不處理，照一頁交出。這是已知限制，見風險章節。 |
| 同一工作裡兩個檔案雜湊相同，頁面編號會撞 | 1.4 已先處理重複；使用者堅持兩份都留時，在編號後加出現序號。 |
| PDF 的行內影像是否被 PDFium 列為影像物件 | 需查證。列不到會低估影像覆蓋率。 |

**設定檔參數。**（初始值，待評測調整）

| 參數 | 預設值 | 單位 |
|---|---|---|
| `preview_long_side` | 1,024 | 像素 |
| `coverage_grid` | 256 | 格／邊 |
| `covering_image_min_coverage`（多大的影像才算「會蓋住文字的大影像」） | 0.5 | 比例 |
| `complex_page_segment_threshold` | 200,000 | 線段 |
| `multi_image_policy` | 合成一份多頁文件 | 選項 |
| `physical_split_min_bytes`（完整版本） | 待評測 | MB |

**可單獨升級的點。**實體拆頁；頁面層級的內容雜湊；用渲染結果算覆蓋率。

### 1.9 逐頁類型判斷

**目的。**告訴後面每一頁該怎麼對待：要不要找四角與攤平（②），走檔案讀取還是影像辨識（③）。

先講清楚兩個標籤的分工，以及一個歸類決定：

- `input_type` 是固定的五種：原生 PDF、掃描 PDF、截圖、照片、混合。
- `capture_kind` 是補充標籤：軟體匯出、平台掃描、相機拍攝、螢幕擷取、未知。它回答「這些像素是怎麼來的」。例如「掃描 PDF」加「相機拍攝」，代表有人用手機拍照後包成 PDF，②就知道可能還要攤平。
- **歸類決定：掃描器產生的影像檔（TIFF、JPEG）歸入「掃描 PDF」這個類型。**類型名稱不改，檔案是不是 PDF 另看 `container_format`。理由：它和掃描 PDF 的頁面在下游的處理完全相同（沒有透視、解析度標記可信）。從軟體直接匯出的影像（例如把簡報另存成 PNG）歸入「截圖」，理由相同：沒有透視、沒有感光雜訊、實際尺寸不明。
- 「混合」的定義：同一頁同時需要檔案讀取與影像辨識兩條產線。檔案層級的混合（有些頁原生、有些頁掃描）不需要特別處理，因為類型本來就是逐頁給的；`summary` 會列出各類頁數。

**做法（PDF 頁）。**用 1.8 的統計量，照順序套規則。門檻皆為初始值，待評測調整。

| 順序 | 條件 | 判定 | 初始信心值 |
|---|---|---|---|
| 1 | 沒有文字、影像、路徑 | 原生 PDF，加警告「空白頁」 | 1.00 |
| 2 | C ≥ 0.95 且 V = 0 | 掃描 PDF | 0.99 |
| 3 | 0.85 ≤ C < 0.95 且 V = 0 | 掃描 PDF | 0.85 |
| 4 | C ≥ 0.85 且 V > 0 | 混合 | 0.70 |
| 5 | C < 0.30 且（V ≥ 20 字或 S > 0） | 原生 PDF | 0.99 |
| 6 | 0.30 ≤ C < 0.60 | 原生 PDF | 0.90 |
| 7 | 0.60 ≤ C < 0.85 | 原生 PDF，`alternates` 列「混合」 | 0.70 |
| 8 | 其餘（C < 0.30，但字很少、也沒有路徑；例如整頁只有一張小圖或幾個字） | 原生 PDF | 0.80 |

只有不可見文字、沒有整頁影像的頁面，照上表判為原生 PDF，另加警告「含不可見文字」。那些文字屬於畫面上沒留下痕跡的東西，怎麼處理由③決定。

三點說明：

- V 只算「看得到」的字。帶隱藏文字層的掃描頁，V 是 0，自然落在「掃描 PDF」，不會被誤當原生。隱藏文字層另由 1.10 標記。
- 規則 4 刻意偏向「混合」。整頁影像加上可見文字有兩種可能：掃描頁被加了頁碼或戳記；或是設計稿用了滿版底圖。①分不出來。判成混合的代價，是③對底圖多跑一次文字偵測，便宜。把掃描頁判成原生的代價，是整頁內容留在圖裡不能編輯，昂貴。所以偏向混合，並把信心值設在中間區，請③細判。
- 規則 5 到 7 的頁面可能含有大張圖片。圖片裡有沒有字、要不要辨識，由③決定；①只在 `pdf_page.images[]` 提供清單。

PDF 頁的取得方式：原生 PDF 記「軟體匯出」。掃描 PDF 與混合頁看三個線索：內嵌影像有相機 EXIF（偏相機拍攝）；頁面尺寸是標準紙張且有效 dpi 是常見的掃描解析度（偏平台掃描）；Producer 符合掃描軟體比對表（偏平台掃描；比對表需查證）。都沒有就記「未知」。

**做法（影像）。**每條線索給一個分數，偏照片為正、偏截圖為負。分數加總後轉成 0 到 1 的信心值。初始權重由工程師手調，之後用標註過的真實影像重新擬合。像素類的線索在正規化影像上抽樣計算，單張耗時目標在 100 毫秒以內（初始值，待評測調整）。

| 線索 | 偏向 | 強度 | 備註 |
|---|---|---|---|
| 上傳途徑是網頁相機拍攝 | 照片 | 決定性 | 來源已知，直接定案。 |
| 有曝光時間、光圈、ISO、焦距等拍攝資訊 | 照片 | 強 | 沒有不代表不是照片：轉傳過的照片常被去除這些資訊。 |
| 完全平坦區塊的比例高 | 截圖 | 強 | 把影像切成小方塊，數「方塊內像素幾乎沒有變化」的比例。截圖有大片純色；照片連白紙都有感光雜訊。過曝成全白的區塊要先排除。 |
| 平滑區域的雜訊水準接近 0 | 截圖 | 強 | 與上一條互補。 |
| 邊緣集中在正水平與正垂直，且邊界銳利 | 截圖 | 中 | 照片有透視造成的斜線與失焦的軟邊。 |
| 像素尺寸等於已知螢幕解析度或其整數倍 | 截圖 | 中 | 比對表放設定檔，要持續維護。 |
| 像素尺寸等於已知的相機感光元件輸出尺寸 | 照片 | 中 | 同上。 |
| 整張影像有緩慢的亮度變化或四角偏暗 | 照片 | 中 | 光源不均與鏡頭暗角。 |
| 格式是 PNG | 截圖 | 中 | |
| 格式是 HEIC | 照片 | 中 | 截圖是否可能存成 HEIC，需查證。 |
| 影像邊緣有整排同色的邊條 | 截圖 | 弱 | 狀態列、黑邊。 |
| 檔名含截圖字樣 | 截圖 | 弱 | 檔名可以隨意改。各作業系統的截圖檔名規則與拍攝資訊標記需查證。 |
| 解析度標記是 72、96、144 dpi | 截圖 | 弱 | |

影像判成「掃描 PDF」（取得方式為平台掃描）只在證據很強時成立，至少符合一項：解析度標記是常見掃描解析度，而且像素尺寸換算後是標準紙張（誤差 2% 以內）；寫檔軟體或廠牌欄位符合掃描器比對表；影像是 1 位元黑白或傳真式壓縮的 TIFF。否則不判成掃描，因為把手機照片錯當掃描會跳過攤平，代價高。

信心值的處理（信心值閘門在本階段的具體做法）：

| 信心值 | 影像 | PDF 頁 |
|---|---|---|
| ≥ 0.90 | 直接採用。 | 直接採用。 |
| 0.60 到 0.90 | 採用，`alternates` 列出次要候選。畫面上顯示可一鍵改判的提示，不打斷流程。 | 採用，`alternates` 列出次要候選，交③細判。不問使用者：這個區間的 PDF 頁很多（滿版底圖的簡報都在這裡），而且③有能力自己分辨。 |
| < 0.60 | 最笨版本：一律按「照片」處理並請使用者確認。完整版本：先交給小模型分類器，仍低才問使用者。 | 規則表的最低值是 0.70，目前不會出現。校準後若出現，處理方式同上一列。 |

拿不準時預設按「照片」處理的理由：②對照片會找四角；找不到時應該退回「整張影像就是頁面」，結果和截圖一樣。反過來把照片當截圖，就完全不會攤平。這個預設成立的前提是②有這個退路，需與②的文件核對。

**常見失敗與對策（判錯的後果與補救）。**

| 實際 | 判成 | 後果 | 補救 |
|---|---|---|---|
| 原生 PDF | 掃描 PDF | 丟掉檔案裡的精確文字，改用辨識。字可能錯，還原度報告從「精確擷取」降級。 | ③細判時會看到 `pdf_page.stats` 裡有大量可見字；使用者修正單。 |

| 照片 | 掃描 PDF（平台掃描） | 同上，而且會誤信解析度標記。 | 判成掃描的門檻設得很高。 |

### 1.10 假原生初判

**目的。**有些 PDF 看起來有文字，其實文字不能用。①用便宜的統計標出嫌疑，讓③知道哪些頁要細查。①只記錄，不改判類型，也不決定產線。

**做法。**三種假原生各一組規則。門檻皆為初始值，待評測調整。

**(a) 隱藏的 OCR 文字層。**掃描軟體做完文字辨識後，常把結果以「不可見文字」疊在掃描影像上，方便搜尋與複製。這些文字的內容與位置都是那套軟體估的，品質不明。

| 條件 | 嫌疑 | 初始信心值 |
|---|---|---|
| 影像聯集覆蓋率 ≥ 0.85，且（不可見字數 + 被遮住字數）÷ 總字數 ≥ 0.90 | 高 | 0.95 |
| 同上，但比例在 0.10 到 0.90 之間 | 中 | 0.60 |
| 另外，Producer 符合文字辨識軟體比對表（比對表需查證） | 等級不變 | 在上面的數值上加 0.03，上限 0.99 |

查證紀錄提醒：光靠渲染模式 3 不夠，還有「不透明度為 0」與「被後畫的物件蓋住」兩種不可見（見 research/pdf.md）。①處理渲染模式與「被大影像蓋住」兩種；不透明度為 0、白字、被裁切掉的文字留給③。對③有用的一點：隱藏文字層雖然不能當真，但可以當辨識的候選字來源，要不要用由③決定。

**(b) 文字已轉外框。**設計稿交印前，常把文字轉成純圖形，這樣不必附字型。頁面上看得到字，檔案裡卻沒有文字物件。

| 條件 | 嫌疑 | 初始信心值 |
|---|---|---|
| 文字覆蓋率 < 1%，影像聯集覆蓋率 < 0.5，路徑線段數 ≥ 2,000，且「只填色、不描邊、含曲線」的路徑占比 ≥ 0.6 | 中 | 0.60 |
| 同上，但頁面另有相當數量的可見文字（部分轉外框，常見於標題與商標） | 低 | 0.40 |

這一項用便宜的統計本質上判不準：插畫與圖表也是一堆填色曲線。所以①最高只給「中」，一律交③用渲染後的文字偵測確認。

**(c) 缺 Unicode 對照表。**PDF 裡的文字存的是字形代碼。沒有對照表，就不知道每個代碼是哪個字，抽出來是亂碼。

| 條件 | 嫌疑 | 初始信心值 |
|---|---|---|
| 字型沒有 ToUnicode，且是用 Identity 編碼的複合字型（中日韓文件最常見的出問題組合） | 高 | 0.90 |
| PDFium 回報 Unicode 對照有誤的字數 ÷ 總字數 ≥ 0.05 | 高 | 0.95 |
| 抽出的文字中，私用區字元（Unicode 留給各家自訂、沒有公定意義的字碼）與替代字元（代表「無法辨認」的符號）的比例 ≥ 0.05 | 中 | 0.75 |
| 字型沒有 ToUnicode，但是用標準編碼的簡單字型 | 低 | 0.20 |
| 字型是 Type 3（每個字形都是一段自訂繪圖指令）且沒有 ToUnicode | 中 | 0.60 |

沒有 ToUnicode 不一定讀不出字：用標準編碼的字型仍可正確對應，所以要分情況。查證紀錄的實測顯示，拿掉 ToUnicode 後 PDFium 會回傳原始字碼並標示對照有誤（見 research/pdf.md），這是最直接的證據。①把受影響的字型編號與字數比例記下來，③可以只對用到這些字型的文字改走影像辨識，其餘照常。

**①抓不到的第四種情況。**有對照表，但對照表是錯的（有些文件為了防複製故意打亂）。便宜的統計看不出來，只能由③抽幾行做影像辨識，和抽出的文字比對。本文件把它列為交給③的事項。

**輸入與輸出欄位。**輸入：`pdf_page.stats`、`pdf_meta.fonts[]`、`pdf_page.fonts_used[]`、`pdf_meta.info.producer`、使用者送給 1.10 的修正單。輸出：`pages[].pseudo_native.hidden_ocr`、`outlined_text`、`missing_unicode`，各含嫌疑等級、信心值、來源類型（量測）、寫入者、證據數值、受影響的字型編號。

**信心值依據。**各項比例離門檻多遠。字型層的判斷（有沒有 ToUnicode、是什麼編碼）是確定性的讀取；「會不會因此讀不出字」才是推論。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 隱藏文字不是用渲染模式 3，而是畫在影像底下 | 用「被遮住字數」補上。Form 物件巢狀時繪製順序要攤平後才比得準；PDFium 的做法未實測，需查證。 |
| 向量插畫被誤標為轉外框 | 可接受。①只給「中」，③確認後才改走辨識；代價只是多一次文字偵測。 |
| 只有標題轉外框，內文是真文字 | 頁面層旗標標「低」；區域層的判斷在③。 |
| PDFium 對 Type 3 字型、只靠預定義對照表的中日韓字型的實際表現 | 查證紀錄列為未知（見 research/pdf.md 的「查不到的事」）。要用真實檔案測，需查證。 |
| 逐字統計在超大頁面上太慢 | 套用每頁時間上限；逾時就抽樣統計，並在證據裡註明是抽樣。 |

**設定檔參數。**（皆為初始值，待評測調整）

| 參數 | 預設值 | 單位 |
|---|---|---|
| `hidden_ratio_high` | 0.90 | 比例 |
| `hidden_ratio_low` | 0.10 | 比例 |
| `outline_text_coverage_max` | 1 | % |
| `outline_min_segments` | 2,000 | 線段 |
| `outline_filled_curve_ratio_min` | 0.6 | 比例 |
| `unicode_error_ratio_high` | 0.05 | 比例 |
| `pua_ratio_mid` | 0.05 | 比例 |
| `ocr_software_patterns` | 待建立 | 清單 |

**可單獨升級的點。**每一種假原生的規則各自獨立，可以分開加強。可加第二個解析器（pdfminer.six，MIT，見 research/pdf.md）交叉比對抽出的文字。

### 1.11 使用者意圖

**目的。**把使用者要什麼記清楚，讓後面各階段照著做。也讓使用者提供檔案裡看不出來的資訊（尺寸、來源軟體）。

**做法。**在上傳畫面或 API 請求裡收下選項，驗證後補上預設值。每個欄位記錄它是使用者指定的，還是採用設定檔預設的。使用者明確指定的值，信心值 1.0。

| 選項 | 欄位 | 可選值 | 不指定時的預設 | 影響哪些下游階段 |
|---|---|---|---|---|
| 輸出格式（可複選） | `output_formats` | PPTX、Google Slides、Word、Excel、Illustrator（文字可編輯的 PDF）、InDesign（IDML）、模板 | 網頁上必選；API 預設 PPTX | ⑥決定跑哪些輸出器。⑦決定做哪些目標驗證。⑤決定目標是求「原值」還是求「最簡潔且渲染一致」（要看輸入與輸出是否同源同格式）。④在選了 Word 可重排或 Excel 時要多做閱讀順序或表格結構。 |
| Word 模式 | `word_mode` | 版面固定、可重排 | 版面固定 | ④⑤⑥。可重排需要閱讀順序、分節、分欄、清單、定位點（R5）。 |
| 用途模式 | `purpose_mode` | 檔案急救、靈感模板 | 檔案急救 | ③的取捨（急救重文字正確，模板重乾淨底圖）。④是否強化網格與空間骨架。⑤⑥是否只留版面骨架。⑦的評分權重。 |
| 已知尺寸 | `known_size` | 標準紙張、簡報比例、自訂寬高與單位、不知道 | 不知道 | ②。寫入頁面規格的實際尺寸，來源為使用者輸入，信心值 1.0。這是 R4 的主要解法。 |
| 語言（可複選） | `languages` | 繁體中文、英文 | 繁體中文加英文 | ③選辨識模型與字典。⑤選字型候選與避頭尾規則。 |
| 書寫方向 | `writing_direction` | 橫排（直排為預留值，目前選不到） | 橫排 | ③④。欄位先留著。 |
| 頁面範圍 | `page_range` | 全部，或指定頁碼 | 全部 | ①的 1.8。 |
| 來源軟體提示 | `source_software_hint` | 不知道、PowerPoint、Word、Keynote、Illustrator、InDesign、Canva、其他 | 不知道 | ⑤的來源軟體判斷（R3）。使用者的說法比 Producer 字串可靠。 |
| 影像類型提示 | `image_type_hint` | 自動、截圖、照片、掃描 | 自動 | ①的 1.9。指定後直接定案。 |
| 權利聲明 | `rights_declared` | 已勾選、未勾選 | 未勾選就不能送出 | 平台（R8）。 |
| 訓練同意 | `training_consent` | 同意、不同意 | 不同意 | 平台（R7）。未同意的檔案不進任何訓練或評測資料。 |

驗證規則的例子：選了 Excel 但輸入是照片，提醒「只會輸出偵測到的表格」。選了直排，回報目前不支援。自訂尺寸的長寬比與頁面明顯不符（差距超過設定值），提醒但不擋。

**輸入與輸出欄位。**輸入：意圖表單、設定檔預設、送給 1.11 的修正單。輸出：`intent` 的各欄位，每欄含值、是否為預設、來源類型、寫入者、欄位雜湊。

**信心值依據。**使用者指定的值，信心值 1.0，來源類型「使用者」。採用預設的欄位不是量測也不是推論，所以不給信心值，只標記「採用預設」。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 使用者不知道怎麼選 | 每個選項都有預設；畫面上只把輸出格式設為必選。 |
| 使用者填的尺寸是錯的 | 照共同規則，使用者的值信心 1.0、不覆蓋。②發現長寬比矛盾時發警告，請使用者再確認。 |
| 使用者事後想加一種輸出格式 | 送修正單到 1.11。靠 1.4 的分欄位雜湊，②③④命中快取，不必重跑辨識。 |
| 選項之間互相矛盾 | 在這一步擋下並說明，不要帶到下游才失敗。 |

**設定檔參數。**

| 參數 | 預設值 | 單位 |
|---|---|---|
| `default_purpose_mode` | 檔案急救 | 選項 |
| `default_languages` | 繁體中文、英文 | 清單 |
| `default_writing_direction` | 橫排 | 選項 |
| `default_word_mode` | 版面固定 | 選項 |
| `api_default_output` | PPTX | 選項 |
| `known_size_aspect_warn`（使用者尺寸與頁面長寬比的差距超過就提醒） | 5 | % |

**可單獨升級的點。**新增輸出格式或選項只要加欄位，並標明哪個下游階段讀它。可依頁面長寬比在畫面上建議輸出格式（橫式建議簡報，直式建議文件），這是畫面層的建議，不寫進 SourceDoc。

### 1.12 組裝 SourceDoc 與建立逐頁工作

**目的。**把前面的結果合成一份完整、驗證過、不可改的 SourceDoc，交給②開始逐頁平行處理。

**做法。**

1. 套用使用者修正單。使用者改過的欄位蓋掉規則算出的值，信心值 1.0，來源類型「使用者」。每次重跑都重新套用，所以不會被新的規則結果覆蓋。
2. 驗證結構：必填欄位齊全、數值在合理範圍、每個參照都指得到檔案。
3. 計算 `summary` 與警告總表，回給畫面。
4. 封存：SourceDoc 寫入只能寫一次的儲存位置。因修正單重跑時產生新的一輪，舊的一輪保留不動。
5. 把正規化檔與預覽圖從隔離儲存區移到正式儲存；原始檔留在隔離儲存區，只有本階段重跑時讀得到。
6. 為每一頁建立一個工作單位（文件編號、輪次、頁面編號），交給②。①②③是逐頁平行的。
7. 有擋路的問題（要密碼、要權利聲明）就停在「等待使用者」，不建立工作單位。

重跑時的行為：內容沒變的頁面，`page_id` 與 `page_digest` 都不變，下游直接命中快取。

**輸入與輸出欄位。**輸入：1.1 到 1.11 的全部輸出、修正單。輸出：完整的 SourceDoc（`doc_id`、`round`、`schema_version`、`writer`、`retention_deadline`、`summary`、`pages[].page_digest`）、逐頁工作單位。

**信心值依據。**不產生新的信心值。

**常見失敗與對策。**

| 失敗 | 對策 |
|---|---|
| 隔離環境吐出的資料結構不對或過大 | 驗證不過就整個工作失敗，不接受部分結果。 |
| 修正單指到不存在的頁面編號 | 拒絕該修正單並回報；其他修正單照常套用。 |
| 使用者連續改意圖，產生很多輪 | 每輪只是一份小的 JSON；大檔案（影像、PDF）以內容雜湊去重，不重複存。 |
| 到了保留期限 | 連同所有輪次與衍生檔一起刪除。 |

**設定檔參數。**

| 參數 | 預設值 | 單位 |
|---|---|---|
| `sourcedoc_bytes_max` | 20 | MB |
| `rounds_max_per_job` | 50 | 輪 |
| `wait_for_user_timeout` | 72 | 小時 |

**可單獨升級的點。**結構版本升級時提供舊版 SourceDoc 的轉換；逐頁工作的排程優先序（先做使用者正在看的那一頁）。

三條補充規則：

- 「這頁的原生文字不可信，改走影像辨識」若來自驗證或 AI，請送③，不送①。產線的最終決定在③；①的假原生旗標只是證據。
- 「頁面要轉 90 度」請送②。①只照檔案標記機械地套用方向。
- 使用者來源的修正，信心值 1.0。之後不管哪個來源的修正單讓①重跑，都不覆蓋它；只有使用者自己能再改。

## 如何評測這個階段

合格線皆為初始值，待評測調整。

| 指標 | 定義 | 單位 | 初始合格線 |
|---|---|---|---|
| PDF 頁類型準確率 | 判定與標註一致的頁數 ÷ 總頁數 | % | ≥ 99 |
| 影像類型準確率 | 同上，對影像 | % | ≥ 97 |
| 高代價錯誤率 | 照片被高信心（≥ 0.90）判成截圖或掃描的張數 ÷ 照片總張數 | % | ≤ 0.5 |
| 隱藏文字層召回率 | 有標出嫌疑（中以上）的頁數 ÷ 實際有隱藏文字層的頁數 | % | ≥ 98 |
| 缺 Unicode 對照召回率 | 同上 | % | ≥ 99 |
| 轉外框召回率 | 同上 | % | ≥ 85（初判；其餘由③補） |
| 假原生初判誤報率 | 標了嫌疑但實際正常的頁數 ÷ 正常頁數 | % | ≤ 10 |
| 信心值校準誤差 | 把判定依信心值分組，各組「平均信心值」與「實際正確率」的差距，依組別大小加權平均 | 百分點 | ≤ 5 |
| 解析成功率 | 成功交出 SourceDoc 的檔案數 ÷ 合法檔案數 | % | PDF ≥ 99.5；影像 ≥ 99.9 |
| 壞檔修復率 | 修復後可用的檔案數 ÷ 壞檔測試集檔案數 | % | ≥ 80 |
| 方向正確率 | 八種方向標記 × 每種格式的測試檔，轉正結果正確的比例 | % | 100 |
| 色彩轉換誤差 | 帶描述檔的色塊影像，轉換後與參考值的色差。用 ΔE2000 計算，這是業界常用的色差公式，數值愈小愈接近 | ΔE | 平均 ≤ 1.0；最大 ≤ 3.0 |
| 中繼資料正確率 | 讀出的欄位與標準答案完全一致的比例 | % | ≥ 99.9 |
| 惡意與炸彈樣本攔截 | 被拒絕或在限額內終止的樣本數 ÷ 樣本總數 | % | 100；且隔離環境零逃逸、工作節點零當機 |
| 頁面編號穩定性 | 同一檔案重跑後頁面編號完全相同的比例 | % | 100 |
| 快取正確性 | 同檔同設定必命中；任何位元組不同必不命中 | % | 100 |
| 處理時間 | 第 95 百分位的整階段耗時 | 秒 | 單張影像 ≤ 2；20 頁 PDF ≤ 5；200 頁 PDF ≤ 30 |

需要的標準答案：

| 測試集 | 內容 | 標註 |
|---|---|---|
| 真實 PDF 集 | 依來源軟體分層（PowerPoint、Word、Keynote、Illustrator、InDesign、Canva、瀏覽器列印、掃描器、掃描 App、文字辨識軟體） | 每頁的輸入類型、取得方式、三種假原生的有無、製作軟體 |
| 影像集 | 各作業系統與裝置的截圖（含被通訊軟體重新壓縮過的）、文件與海報的照片、翻拍螢幕、掃描影像、軟體匯出圖 | 每張的輸入類型與取得方式 |
| 格式符合性集 | 八種方向 × 各格式；各種色彩描述檔與位元深度；透明、多影格、HDR | 轉正後的參考影像、色塊參考值 |
| 壞檔與惡意集 | 截斷檔、索引表損壞檔、解壓縮炸彈、超大尺寸影像、多格式混體檔、加密檔 | 預期的處理結果（修復、拒絕、原因碼） |
| 中繼資料集 | 已知答案的 PDF 與影像 | 每個欄位的正確值 |

兩個限制：真實檔案只能來自自己製作、公開授權、或使用者明確同意的來源（R7）。公開的壞檔與惡意樣本集有哪些、授權如何，需查證。

信心值的校準一律用真實檔案，不用合成資料（R6）。①的判斷本來就是對真實檔案做的，沒有理由用合成資料。

## 最笨版本與完整版本

最笨版本的目標：打通「原生 PDF → PPTX」這條線。只收 PDF，沒有 AI，沒有迴圈。

| 步驟 | 最笨做法 | 完整做法 | 建議何時升級 |
|---|---|---|---|
| 1.1 接收 | 只有網頁上傳，只收 PDF；單一大小上限 | 三個入口、全部格式、分段續傳、依方案分級的限額 | 要開放影像輸入時；有 API 客戶時 |
| 1.2 類型判定 | 只檢查 PDF 檔頭 | 完整比對表、混體檔偵測、副檔名不符的提示 | 與 1.1 開放影像同時 |
| 1.3 安全檢查 | 獨立行程加記憶體與時間上限；加密檔一律拒絕；不掃毒 | 完整隔離環境、掃毒、密碼流程、權限旗標政策、主動內容清單 | **對外開放任何陌生使用者上傳之前，隔離環境必須到位。**密碼流程等真實使用者被擋的比例高了再做 |
| 1.4 雜湊與重複 | 只算 SHA-256，不做快取 | 快取、同工作去重、像素雜湊、感知雜湊 | 迴圈（修正單重跑）上線時就需要快取 |
| 1.5 PDF 修復與正規化 | 用 pikepdf 開啟再存一份；打不開就拒絕 | 修復警告分級、主動內容移除、雙解析器核對、部分救回的流程 | 真實檔案的打不開比例超過 0.5% 時 |
| 1.6 影像解碼與正規化 | 不做（不收影像） | 全部項目 | 開放影像輸入時。先做 JPEG 與 PNG 的方向與色彩；HEIC、深度、HDR 排後面 |
| 1.7 中繼資料 | 讀 Producer、Creator、頁框、旋轉、頁數 | 加 XMP、字型清單、圖層、結構標記、註解 | ⑤開始做來源軟體判斷與字型定案時要字型清單與 XMP；④做 Word 可重排時要結構標記 |
| 1.8 拆頁與統計 | 頁面清單與編號；統計只算可見字數、不可見字數、最大影像覆蓋率 | 完整統計、預覽圖、線索、頁面雜湊 | 遇到橫條掃描或圖層式掃描判錯時，加聯集覆蓋率 |
| 1.9 類型判斷 | PDF：有可見字就是原生，否則掃描。影像：不適用 | 完整規則表、取得方式、影像線索表、信心值閘門、小模型分類器 | 開放掃描 PDF 與影像時做規則表；真實資料上影像準確率低於合格線時加小模型 |
| 1.10 假原生初判 | 只算不可見字比例與 Unicode 對照有誤比例；有嫌疑就告訴使用者「這頁目前不支援」 | 三組完整規則、被遮住字數、字型層判斷、交給③細判 | ③的影像辨識產線上線時，假原生頁才有地方可去 |
| 1.11 使用者意圖 | 寫死：輸出 PPTX、檔案急救、繁體中文加英文 | 全部選項、驗證、分欄位雜湊 | 第二種輸出格式上線時 |
| 1.12 組裝 | 寫出一份 JSON，直接呼叫下一階段 | 結構驗證、封存、輪次、逐頁工作單位、等待使用者的狀態 | 逐頁平行與修正單上線時 |

## 風險與需查證

### 對照九個已知高風險點

| 風險 | 與①的關係 | ①怎麼處理 |
|---|---|---|
| R1 驗證引擎不是目標引擎 | 無直接關係 | ①不渲染供比對用的影像。只記使用者選了哪些輸出格式，供⑦決定做哪些目標驗證。 |
| R2 字型 | 間接 | ①記「檔案宣稱的字型名稱」與是否內嵌，當⑤的證據。它不是「推論的字型名稱」，也不是「驗證用的替代字型」。不取出內嵌字型程式（見 research/fonts.md）。 |
| R3 「原始設定」只在同源同格式時有定義 | 直接 | ①原樣交出 Producer、Creator、XMP，並收使用者的來源軟體提示。①不判斷來源軟體。提醒⑤：這些字串可能空白或被改寫，不能當唯一依據。 |
| R4 絕對尺度不可觀測 | 直接 | ①不推論尺寸。它保留所有可能有用的線索（頁框、使用者單位倍率、解析度標記與可信度提示、焦距、深度影像、機型），並在意圖表單請使用者填已知尺寸。截圖的解析度標記明確標為不可信。 |
| R5 Word 可重排需要的不是框 | 間接 | ①記錄 PDF 是否帶結構標記（Tagged PDF）、文件語言、閱讀方向，當④的證據。使用者選可重排模式時記進意圖。 |
| R6 信心值連乘與校準失準 | 直接 | ①只有少數幾個彼此獨立的判斷。建議下游不要把①的信心值乘進元素層級的信心值；它只用來決定「要不要問使用者」和「要不要兩條產線都跑」。校準只用真實檔案。 |
| R7 資料飛輪與隱私互斥 | 直接 | 保留期限寫進 SourceDoc，預設 30 天。訓練同意是意圖欄位，預設不同意。快取只在同一使用者內。紀錄檔不含檔案內容與中繼資料的值。丟棄 GPS 與裝置序號。測試集只用有授權或已同意的檔案。 |
| R8 法律與濫用 | 直接 | 權利聲明為必填。加密與權限旗標有明確政策。偵測數位簽章並提示。①是唯一能在處理前擋下檔案的位置，所以保留稽核紀錄的掛點（保留多久見待你決定的問題）。①不判斷「這是不是證件或合約」，那需要辨識內容，本階段做不到。 |
| R9 Illustrator 拆字、Google Slides 再轉一次 | 無直接關係 | ①只記使用者選了這兩種輸出，由⑥⑦處理。 |

### 本階段特有的風險

1. **照片被當成截圖，後面沒有任何一道驗證抓得到。**7A 拿工作影像當基準，工作影像歪了它也看不出來。目前的防線是：拿不準就按照片處理、②發現透視線索時警告、使用者改判。這個風險要靠影像類型準確率與高代價錯誤率兩個指標盯著。
2. **「掃描 PDF」這個類型涵蓋了掃描器產生的影像檔。**下游若假設「掃描 PDF 一定有 PDF 頁框」就會出錯。下游要看 `container_format`。這個歸類需要各階段文件一致，見待你決定的問題。
3. **規則 4 會把「滿版底圖加文字」的設計稿判成混合。**這是刻意的，代價是③多跑一次文字偵測。若③沒有對應的細判，簡報與海報會大量落入混合，處理時間增加。需與③的文件核對。
4. **解碼器的安全漏洞。**所有防護都建立在隔離環境上。隔離環境沒到位之前，不能對外開放上傳。
5. **便宜的覆蓋率是用外框近似的。**被裁切的大影像會讓覆蓋率高估，可能把原生頁推向混合。影響有限（偏向較安全的一側），但會拉高成本。
6. **一頁多版。**講義一頁六格、書本跨頁掃描，①照一頁交出。目前沒有任何階段負責把它拆開。使用者只能自己先裁切。
7. **PDFium 的實驗性介面。**逐字的 Unicode 對照錯誤、字型資訊等函式都標為實驗性，官方保留更動的權利（見 research/pdf.md）。要鎖定 PDFium 版本，升級時重跑本階段的評測。
8. **製作軟體、掃描軟體、螢幕解析度等比對表會過時。**新手機、新軟體版本不斷出現。比對表放設定檔，要有人定期維護。
9. **桌面版。**沒有上傳、沒有伺服器的隔離環境、沒有掃毒服務。①的步驟不變，但 1.1、1.3 的實作要另寫。pikepdf 的 macOS 安裝包內容有一處官方文件自相矛盾，出貨前要打開實際檔案確認（見 research/pdf.md）。

### 與其他階段的交界假設（需核對）

- ②把①的正規化影像當作「原圖」；PDF 頁的工作影像由②產生。
- ②在照片找不到四角時，退回「整張影像就是頁面」。
- ②決定用哪個頁框當頁面，並決定頁面方向。
- ②讀 `capture_kind`：掃描 PDF 加相機拍攝時考慮攤平。
- ③讀 `pseudo_native` 與 `input_type.alternates` 做細判，並自行決定產線。
- ③對混合頁與大張內嵌影像做文字偵測。
- ③的元素編號包含 `page_id`。
- 修正單的目標編號可以是檔案編號或頁面編號。
- 下游各階段的快取鍵只放它實際讀的 SourceDoc 欄位。
